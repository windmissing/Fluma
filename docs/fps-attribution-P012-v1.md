## 2. 当前帧时间去向（s106 EAB+C 全开，2897 帧分解）

### 2.1 分段统计（WS_FRAME 遥测：frameTimeMs / physicsTimeMs / substeps）

| 段 | 帧数 | frameTimeMs p50/p95 | physicsTimeMs p50/p95 | render+其它 p50/p95 |
|---|---|---|---|---|
| 静止（substeps=0，dormant 跳过物理） | 1396 (48%) | **17 / 18** | 0（跳过） | ≤17（纯渲染+vsync） |
| 动态·轻中载（physics≤40ms） | 1292 | **28 / 35** | 13 / 20 | **15 / 19** |
| 动态·重载倾斜（physics>40ms） | 209 | 106 / 129 | **90 / 111** | 15 / 21 |
| 全体 | 2897 | 24 / 104 | 11 / 87 | 16 / 19 |

### 2.2 逐项归因

**① 物理子步（动态帧第一大头，重载段决定性）**
- 轻中载动态：physics p50 13ms（substeps=2 × ~6.5ms/子步，128 列 × 192 行高度场多账本更新）
- 重载倾斜（±80° 瀑布流）：physics p50 **90ms**、max 111ms——大倾斜触发的全列雪崩式质量搬运是物理成本上限形态
- 对照（obs3v2 run-001 普通静置采集）：physics p50 8ms，与 s106 轻载一致
- **物理是重载段帧时的 85%**（90/106），任何渲染优化对重载段无效

**② Canvas2D 渲染+合成（render+other p50 15ms，动态/静止通用）**
- 构成：EAB+C 全链 draw 计数 ~52（E 档游程 fillRect ~10 + A 档雾 12 档 × 组 + C 层理 9 + B 档颗粒 drawImage 12-36 + 公共 4）+ Canvas 提交后的 RS（RenderService）光栅化/合成（不归应用控制）
- 静止帧 frame p50 17ms：物理为 0 时帧时仍 17ms → **渲染+合成+vsync 等待 ≈ 17ms**，即当前 Canvas2D 链在 60Hz 节拍（16.7ms）内刚好占满一拍
- 直方主峰 25-29ms（254+143+111 帧）：动态帧超一拍落到第二拍（2×16.7 附近被工作量推到 25-29）
- 消融证据链（既有）：D1 消融（pattern→纯色）tier3 34/34/36 ≈ tier2；D2（globalAlpha=1.0）无效；B 档 drawImage 平铺化后 tier3 与 tier2 同档——**Canvas2D 侧当前瓶颈不在提交次数**（draw 预算受控），在**每帧全屏重绘的光栅化/合成成本**（~0.9Mpx 画布逐帧全量提交）

**③ 呈现管线/帧调度**
- 帧驱动 = UIContext.postFrameCallback（vsync 对齐）；frameTimeMs 量化在 vsync 节拍附近（静止段 16-18、动态轻载 24-31、无 11.1ms@90Hz 主峰）
- **关键事实：静止段锁定 60Hz 节拍而非 90Hz**——postFrameCallback 每帧全量回调，但渲染+合成工作量 >11.1ms 时无法落在 90Hz 单拍，退化到 60Hz 两拍
- 历史「60 封顶」结论修正：设备面板 90Hz，但应用帧循环从未达到 90Hz 单拍预算（渲染+合成 ~15-17ms > 11.1ms）

## 3. 架构方向评估（只评估不实施）

### ① Canvas2D 逐帧绘制 → 离屏预合成分层（静态层缓存+动态层重绘）

- **原理**：把「不变的层」（容器底色/边框/水面基色/雾静态斑驳/颗粒位图）预合成到离屏画布，每帧 blit 一次；只重绘「变化的层」（沙体轮廓/界面带）
- **既有证据**：PERF 轮 F3 方案曾评估过离屏预合成并**被否决**——当时根因已闭环为 CanvasPattern 采样（改 drawImage 后已消除），离屏未启用；但那是 30fps 口径的归因，100fps 口径下结论不同
- **收益上界估算**：静态层 blit（~0.9Mpx drawImage 1 次 ≈2-4ms）替代 E/A 层全量重绘（~40 draw 提交+光栅化）；动态层只剩沙体三带 + 颗粒 + C 层理。render+other 15ms → 估算 8-11ms——**有望进入 90Hz 单拍（11.1ms）**，但受 ② 中 RS 合成成本下限约束
- **风险**：C 层理位图与平流偏移逐帧变化（warp 跟随材料位移），「静态」边界要重新划分；离屏生命周期管理（§10.3 已预置设计）；几何 epoch 变化时重合成峰值
- **结论：方向有效但不充分**——单独做它到不了 100fps（受 §5 设备上限），能到的是「90Hz 满帧」

### ② 部分硬件加速可行性

- 现状：ArkUI Canvas2D 本身经 RS 走 GPU 合成；**逐 draw 的光栅化已在 GPU**，应用侧无法再「部分加速」单个 Canvas
- 可选路径：NativeImage/XComponent 接 EGL 直接渲染（绕过 ArkUI Canvas，自管 swapchain）——属于 P-013 级改造（新渲染栈），非本任务可评估收益
- DrawHelper/egl 混合：OpenHarmony 无官方「Canvas 部分硬件加速」开关；Canvas 的 `imageSmoothingEnabled` 等属性影响质量不影响提交路径
- **结论：当前架构内无「部分加速」可用项；全量换渲染栈属 P-013 议题**

### ③ 渲染列密度/插值与帧时关系（E3 成本输入）

- E3（网格感消除）拟做列间插值/提高渲染列密度——gap.md 已标注「须与帧时联合评估」
- 成本模型：128 列 → 256 列（r=2），drawSandColumns 的游程 fillRect 数约 ×2（列多一倍、游程段数近似翻倍），C 层理分段数近似 ×2（warp 采样列密度翻倍）——**E3 若走「加列」路线，render+other 预计 15→19-22ms，把 90Hz 单拍可能性直接推远**
- 替代：列间插值（显示层 lerp，物理列不变）成本 O(显示宽度)，在 fillRect 前用平滑曲线 Path 替代逐列矩形——与 C 层理的带曲线 clip 同构，draw 数不增，只有 Path 点数 ×2（2×128→2×256，光栅化成本增量小）
- **结论：给 E3 的输入=优先「曲线 Path 插值」而非「物理/渲染列加密」；后者与 F1 目标直接冲突**

## 4. 可达性判断框架（不预判，列证据边界）

| 方向 | 有望达到 | 证据/上限 |
|---|---|---|
| 离屏预合成分层 | **90Hz 满帧（fps≈90）** | render 15→8-11ms 估算 + RS 合成下限；受 90Hz vsync 封顶 |
| 物理子步优化（重载段） | 重载帧 106→~35ms | physics 90ms 是重载段 85%；优化空间=子步内高度场更新的 JS 数值成本（SIMD/WASM/Worker 化均属改造，本文不评估） |
| 渲染栈更换（XComponent/EGL） | 理论可达 90Hz+ | P-013 级议题；90Hz 面板仍是上限 |
| **fpsP95≥100（G2.7 原指标）** | **当前设备物理不可能** | 实测面板刷新率 90Hz（vsync 封顶 fps≤90）；fpsP95≥100 需 ≥111Hz 面板 |

**交 manager 裁决的三个选项**（本文不预判）：
1. G2.7 指标按设备实际刷新率修订（100→90 或「达设备刷新率」措辞）——需 goals 变更流程
2. 保持 100fps 原指标，升级 P-013 换渲染栈 + 更高刷新率设备——当前 VYG-AL00 无法满足
3. 维持现状：第一梯队 30fps 口径 CLOSED 不动，F1 作为长期项挂起

## 6. 结论摘要

1. **帧时三去向**：物理（重载段 90ms/85%，轻载 13ms）> Canvas2D 渲染+RS 合成（p50 15ms，全屏逐帧重绘的固有成本，与 draw 次数无关——消融已证）> vsync 节拍量化（60Hz 两拍锁死）
2. **100fps 的第一障碍不是代码效率，是设备刷新率 90Hz**——任何软件优化在此设备上的天花板是 90
3. **软件侧可达的现实目标是 90Hz 满帧**：需要「离屏预合成分层（render 15→≤11ms）+ 物理重载段治理（90→≤35ms）」两路并行，均属架构改造，须 manager 裁决立项
4. **E3 与 F1 的成本冲突**：列加密路线会把 render 推到 19-22ms，应改走曲线 Path 插值
5. G2.7 的 fpsP95≥100 与 TC-WS-11 的 30s 连续动态窗口口径未冻结到测量附录——修订指标前须先走 goals 变更
