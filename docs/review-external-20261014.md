## 一、硬伤：参数与阈值不联立（可直接算出，不需跑代码）

### 1.1 TC-WS-08 的两条阈值在当前动力学下不可能同时满足

扬起公式：

```text
band[c] = min(sandTop[c], max(0.5, tan α))     α = 30°  →  band ≤ 0.577 列
lift    = E × rate × band × share × dt
```

`band` 的**上限是与 E 无关的常数 0.577 列**。取 `liftLRate = 0.55/s`、`E = 1`：

```text
每列每秒最多扬起 0.55 × 0.577 ≈ 0.32 列
3 秒全速摇晃 → 约 0.95 列/列
```

| 沙堆平均厚度 sandTop |               峰值悬浮比例 | 判定（要求 ≥ 0.5）   |
| -------------: | -------------------: | -------------- |
|     40 列（正常沙丘） | 0.95 / 40 ≈ **2.4%** | FAIL，差约 20 倍   |
|    1.9 列（几乎铺平） |                ≈ 50% | 勉强达标，但此时不成「沙丘」 |

同时看残余悬浮。沉降是**指数衰减**：

```text
suspFraction(t) = peak × exp(−vH · t / depth)，时间常数 τ = depth / vH
默认几何 waterTop ≈ 110、sandTop ≈ 40 → depth ≈ 70；vH = 16 → τ ≈ 4.4 s
8 秒后：exp(−8 / 4.4) ≈ 0.16
```

两条阈值联立：

- 要 `peak ≥ 0.5` → 需扬起率 ≥ `0.5 × sandTop / 3`
- 要 `residual = peak × exp(−8/τ) ≤ 0.05` → 需 `τ ≤ 3.47 s`

默认参数（`vH = 16`、`liftHRate = 0.35`、`liftLRate = 0.55`）下：

- **peak 严重不足**（正常沙丘只有 2.4%）
- **residual 反而轻松通过**（2.4% × 0.16 ≈ 0.4%）

两个指标一个「必败」一个「必胜」，说明它们没有被放在一起算过。要同时达标，需要**同时大幅重调**：扬起率提高约一个数量级、`vH` 提到 ≥ 20、并重新选定 `depth` 与沙量。

### 1.2 TC-WS-07 倒立 4 秒分选，余量很小

`invert180()` 把**全部**沙转为悬浮并置 `E = 0.8`；E 按 2.2/s 衰减，约 1 秒降到 0.1，之后沉降才主导。

```text
有效沉降 ≈ 3 秒 → 沉积比例 1 − exp(−3 / 4.4) ≈ 49%
重沙（vH=16）沉约 60%，轻沙（vL=6）沉约 29%
```

分选方向正确（重沙先落），但 4 秒内只有约一半沙落地，且 E=0.8 期间扬起与沉降对抗、进一步压低沉积量。`phaseOrderScore ≥ 0.30` 能否达到取决于几何与分选速率，**没有安全余量**。

### 1.3 沉降缺通量限幅，可能触发瞬移硬门槛

安息角有 `maxAvalancheFlux` 限速，**沉降没有**：

```text
depH = min(suspH, suspH · vH · dt / depth)
```

浅水时 `depth → ε`，该式退化为「一帧全沉」。sandTop 单帧跳变可达 `suspH`，而 HG-04 要求**单帧位移 ≤ 0.5 列、≤ 30 列/秒**。需要给沉降加显式 budget 限幅（复用安息角思路）。

## 二、90° 横置与「连续 ±180°」

- 场景二方案 §8.7 明确 `tiltDeg ∈ [−89°, 89°]`，90° 横置「不属于 v1 范围」。
- 架构 §3.7 用 `visualInverted = 90 < |angle| < 270` 加一次 `invert180()` 事件跨过 90°。
- 因此从 0° 到 180° **不是连续求解**，而是「89° 以内连续 + 90° 处一次数据镜像与再悬浮事件」。

由此产生两处需要澄清的措辞冲突：

1. **G3** 写「支持 ±180° 连续重力方向变化」。是允许「事件式跨 90°」，还是要求真正连续过 90°？两者工作量差一个量级。
2. **EC-WS-07 硬门槛 H06** 写「数据模型被倒立分支改写 → FAIL」。而 `invert180()` 的设计恰恰就是改写物理数据。需要明确 H06 是只禁止「渲染分支私改数据」，还是也禁止这个物理事件——否则 tester 按字面就能判 FAIL。

### 7.1 Block 1 · 参数组重调 —— ✅ 通过

联立判据（消去 peak）：`residual / peak = exp(−8·v / depth) ≤ 0.1 → v ≥ depth · ln10 / 8 ≈ 20.2 列/秒`，**只与沉降速度有关、与扬起率无关**。v2.1 的 `vH=64`、`vL=38` 均在可行区内。

- **残余由轻沙尾主导**：重的先沉完，剩下几乎全是轻沙，`τ_L = depth / vL`，故真正卡阈值的是 `vL=38`（这也是必须把 `vL` 从 6 提到 38 的原因）。
- **峰值复算**：`suspH* = liftEff · depth / vH`，`liftEff ≈ 0.577 × 38 ≈ 21.9` → `suspH* ≈ 23.9 列` → `peak ≈ 60%`（平衡值）；3 秒达约 93% → **≈ 55%**。文档 52.8% 略保守，一致。
- ⚠️ **余量薄**：peak 仅高阈值约 3 个百分点，建议给**目标区间**（如 0.55–0.75），别压在阈值边缘。

### 7.2 Block 2 · 沉降通量限幅 —— ⚠️ 机制对，换入同类新问题

### 8.2 复核 A · 速率形式是否真正消除刷新率依赖 ✅

`clippedDt = min(frameDt, 1/30)`；`substeps = (clippedDt <= 1/60) ? 1 : 2`；`substepDt = clippedDt / substeps`。

取 `vSandTopMax=28`，逐档验算：

|   刷新率 | clippedDt | substeps | substepDt |     单子步预算 |   等效速率 | 「单帧 ≤0.5 列」 |
| ----: | --------: | -------: | --------: | --------: | -----: | ----------- |
| 120Hz |     1/120 |        1 |     1/120 |    0.2333 | 28 列/秒 | 0.233 ✅     |
|  60Hz |      1/60 |        1 |      1/60 |    0.4667 | 28 列/秒 | 0.467 ✅     |
|  30Hz |      1/30 |        2 |      1/60 | 0.4667 ×2 | 28 列/秒 | 每子步 0.467 ✅ |

**速率与刷新率无关这一点成立。** 两处附带说明：

- 「物理不随刷新率变化」严格说是 **速率一致**；指数沉降的离散步长误差为 `O(v·dt/depth)`，120Hz 与 60Hz 之间存在约 `0.3%` 的积分差异（文档 `t90` 行写 `0.633~0.635`，正是这个量级）。不构成问题，但措辞上宜写成「速率一致（积分离散差 <0.5%）」。
- 架构 §11.4 已规定 `maxSandTopSubstepDeltaObserved`、`maxSandTopSpeedObserved` 以**子步**为口径，并明确「30Hz 两子步分别检查、不得相加后套用 0.5 列」。这条把 TC-WS-09 的潜在误判堵住了，处理正确。

**唯一遗留**：`test-cases.md:165` 仍写「单帧位移 `<= 0.5` 列」，是渲染帧措辞。与架构口径不一致的后果：30Hz 设备上，一帧两子步合计 0.933 列，tester 若按「渲染帧」读会判 FAIL。**需在 test-cases.md 补一句「本处『单帧』指物理子步；30Hz 一帧含两子步时分别检查」。**

### 8.3 复核 B · 绑定核算的可行域与敏感度 ⚠️

文档 §16.5 给出峰值 `63.6%`、残余 `0.70%`，并声明用一维均匀列模型。我用同一套式子复算，先把稳态条件写出来。

**稳态条件**（沉降与扬起共享预算、沉降优先）：

```text
稳态 ⇒ 扬起速率 = 沉降速率
预算绑定 ⇒ 扬起 = 沉降 = vSandTopMax / 2 = 14 列/秒
沉降速率 = S · v̄ / depth          （S = 悬浮总量，v̄ = 悬浮相的有效沉降速度）
depth = waterTop − sandTop = 70 + S （扬起的沙离开床面 ⇒ 水柱变高）
```

解得

```text
S = 980 / (v̄ − 14)        悬浮比例 f = S / 40 = 24.5 / (v̄ − 14)
```

逐点代入：

| 悬浮相构成       | `v̄` |            预测峰值 `f` | 相对目标带 `0.55~0.75` |
| ----------- | ---: | ------------------: | ----------------- |
| 全重沙         |   64 |                0.49 | **低于下界**          |
| 重:轻 ≈ 50:50 |   51 |                0.66 | 带内                |
| 文档反解值       | 52.5 |           **0.636** | 带内（= 文档值）         |
| 重:轻 ≈ 35:65 |   47 |                0.74 | **压上沿**           |
| 全轻沙         |   38 | >1.0（由 `band` 节流封顶） | **越上界**           |

**结论三条：**

1. **`63.6%` 可复算**，反解 `v̄ = 52.5`，与「重:轻 = 50:50」的 `(64+38)/2 = 51` 基本一致。所以文档这一行**隐含假设悬浮相轻重各半**。
2. **但模型自身参数必然使悬浮相偏轻**：重沙沉降时间常数 `τ_H = depth/64 ≈ 1.5 s` 明显小于轻沙 `τ_L = depth/38 ≈ 2.5 s`，且重沙扬起率更低（`36 < 40`）。按两者联立，悬浮比约 `S_H:S_L ≈ (36·τ_H):(40·τ_L) ≈ 35:65`，对应 `v̄ ≈ 47`、`f ≈ 74%`——**正好落在目标带 `0.75` 的上沿**，不再有余量。
3. 敏感度是**单向**的：`f` 随 `v̄` 下降而急剧上升（`v̄` 每降 2，`f` 涨约 5 个百分点）。所以「峰值 63.6%，余量充足」这个判断对悬浮构成高度敏感，不宜当作稳定结论。

**残余 `0.70%` 复算**：从 `S ≈ 30` 起按 `dS/dt = −S·v̄/(70+S)` 积分 8 秒，得 `S(8) ≈ 0.2 列` → `f_res ≈ 0.5%~0.8%`，与文档 `0.70%` 一致 ✅。

**倒立两行复算**：`sandTop=0`、`depth=110`，随沉积进行 depth 由 110 收到约 70，取程内均值约 92 → 重沙 `1−e^(−64×4/92) ≈ 94%`、轻沙 `1−e^(−38×4/92) ≈ 81%`，与文档 `95.0% / 83.1%` 吻合 ✅。**这两行明显用了「depth 随沉积收缩」的变值 depth**，而峰值那一行只有在 `v̄=52.5` 时才自洽——同一张表里两处口径虽然都能对上，但峰值行的 `v̄` 依据必须写出来，否则复核方无法判断该行是「预测」还是「拟合」。

**建议**：

- §16.5 补一行 `v̄` 的取值与来源（悬浮相重:轻比），并给出 `f = 24.5/(v̄ − 14)` 这条敏感度式；

### 10.2 问题一：蠕变方向疑似写反（需 designer 一句话确认）

坐标系定义（§2.1）：`tiltDeg > 0` 表示**列号增大方向更低**——右列是下坡。

v2.5（§20.1）：「`effectiveTilt > 0` 时**从右列向左列**蠕变」——按 §2.1 的定义，这是**从低处往高处搬**。

矛盾证据：v2.4 §18.2 的哨兵例明确判定「`effectiveTiltDeg=45°`、水平沙面时 `deviation=-1`，**从左列向右列**滑移」——同一个符号约定下，v2.4 说沙往右流，v2.5 说沙往左流，两者不能同时成立。

两种可能：
1. v2.5 的 `effectiveTilt` 符号约定与 `tiltDeg` 相反（新增了取反），若是，必须在 §20.1 显式写出换算关系；
2. 单纯笔误，方向应改为「`effectiveTilt > 0` 时从左向右」。

**风险**：developer 照字面实现 → 沙往山上爬，真机观感直接反物理。这是 v2.5 唯一的阻塞性疑点，一句话确认即可解除。

### 10.3 问题二：蠕变速率与共享预算量级不匹配（「不跟手」的可能真凶）

名义速率核算（`q ≤ bottomCreepRate × dt × min(1, |tilt|/20°)`）：

| 参数 | 倾角 | 名义速率 |
|---|---|---|
| 默认 36 | 10° | 18 列/秒 |
| 默认 36 | ≥20° | 36 列/秒 |
| thick 96 | 10° | 48 列/秒 |
| thick 96 | ≥20° | **96 列/秒** |

对照共享预算：`vSandTopMax = 28 列/秒`，且蠕变还要与沉降、滑移、扬起**分抢**同一份 `remainingSubstepBudget[c]`。

推论：**`bottomCreepRate` 调到 96 在 ≥20° 倾角下完全无效**——名义需求 96 > 预算上限 28，实际有效速率被钳在 ≤28 且通常远小于 28（其余算子先到先得）。这解释了真机现象「调大了还是不跟手」：瓶颈不在平滑参数、不在蠕变速率常数，在**预算饥饿**。

处置建议（按侵入性排序）：
1. **最低成本**：给底层蠕变开独立的预算子通道（如 `vBottomCreepMax ≤ 8~12 列/秒` 从总预算外单列），理由是底层搬运与表层运动在视觉上是两个独立的观感通道，共享预算把它们错误地耦合成了零和；
2. 若不愿意加通道：把 `bottomCreepRate` 默认值直接定义在预算内（≤28），并在 §20.1 写明「名义速率超过预算的部分无效」，避免后续调参误导；
3. 结构性方案见 10.5 的 gravity-advection 路线。

### 10.4 P-011 治理设计 —— 值得固化为团队规范

### 11.1 论文 252 → P-008 解法升级（designer）

当前 `percolationRate = 6/s` 常数的三个物理缺陷，252 的 f_sl 偏析速度律逐项给出修正形式：

| 常数的问题 | f_sl 律对应项 |
|---|---|
| 干湿不分（干沙区也用同一速率） | 压强抑制项 `(C ρ* g d̄ + p)`：p 大分选慢——干沙表层 p≈0 分选快、深埋水下 p 大分选慢，一式自动处理 |
| 不随剪切变（静置也全速分选） | 剪切驱动项 `γ̇`：静置时 γ̇→0，分选自然关闭（治「静置还在跑」） |
| 不随材质变 | 粒径不对称项 `d̄²·(R−1)`：轻重沙粒径比 R 直接进公式 |

关键性质：B=0.3744、C=0.2712、E=2.0957 为**普适常数**（Trewhela et al. 2021 实验全族标定），无需逐材质调参；双线性 `φ_νφ_λ` 结构自动保持 [0,1] 有界（与现有账本的等量对向交换同构）。

**列标量简化落地路径**：
- `γ̇` 用列间差分近似：`|sandTop[c+1] − sandTop[c−1]| / (2dx)`；
- `p` 用上覆沙深近似：`p ∝ sandTop[c]`（水下再乘浮力折减 `(ρ_s−ρ_w)/ρ_s`）；
- `R` 用轻重沙等效粒径比（设计参数，非运行时变量）；
- 适用边界照抄 252：粒径比 ≤ 5 区制内有效，超出不外推。

建议将 P-008 的解法描述从「参数化为 Δρ/μ 相关」升级为「f_sl 律列标量简化版」，理论出处 252.md。

  - 【2026-10-22 引用勘误】原引「253/255」支持本条——经 253 原文核查（JFM 975 A14），253 研究崩塌的摩擦系数选择（起崩角 vs 停止角），**不含深层蠕动机制内容**，不支持此归因，已摘除；255 与 Barker-Gray 2017 是否支持待各自核查后判定。体力驱动蠕动缺失的结论本身不受影响，但证据链需另行补证。

#### v2.11-R1 可复算账本复核确认

designer 产出修订势能 `D_s = s·(tan(θ)·dx − (S_R−S_L))`（冷启动解除）+ 可复算账本并自我判定设计失败。独立复算确认：每子步 gravity 仅分得 5·dt（scale 0.0041），每边每子步 q≈0.000165；5.1s 累计全场最大 |Δbh|=0.0856 ≈ 0.139px，**中央 104 列恒为 0**（均匀势场→均匀边请求→内部列一入一出抵消——「相邻列对向交换」类机制的宿命）；2px 需 |Δbh|≥1.2347 units（pixelsPerModelUnitY=311/192）。判定成立。

#### 双角度滞回方案复核确认（v2.12）

逐边三态状态机正确表达 P&F 滞回路径依赖；excess 以 slopeStop 为目标物理正确；候选取舍（拒绝全局单一状态/单阈值死区）理由成立。**发现窗口边界问题**：搜索窗口 `thetaStart ∈ [25°,30°]` 上端点与 `thetaHardMax=30°` 重合——thetaStart=30° 时滑移起动与硬门槛越界不可区分，有效窗口实为 [25°,30°)，定标时需排除上端点或预留安全边距。另确认 relax 通道在 ±15° 本就活跃（请求 3125/应用 718）——双角度调的是活跃通道，着力点正确。

#### 大角度观测结果（slip-overshoot-v1）与归因

真机 ±45° 过冲实测：**表层滑移大角度下正确触发**（双向 slipTriggered=true，第一类机制大角度验证通过）；但 ① 可见表面坡度峰值仅 ~4°，远未收敛到安息角构型（convergedTo30Deg=false），重沙界面 0px——「滑移表层优先搬轻沙」的理论预测坐实；② **硬门槛被击穿 484 次**（range 违规，首次在有效倾角 24° 时，不变量误差 0.73 > 0.577）。

designer 归因（v2.13，数字独立复算吻合）：**越界不是材料通道推过线，而是参考线自己动了**——倾角从 24° 更新至 36°（tan 从 0.445 跳至 0.727）发生在任何材料 grant 之前，沙面水平、材料未动，残差被动越限。relaxAngle 追不上的主因是 127 边均匀请求内部抵消 + total 限流 9.54%（与 v2.8/v2.11 同源的第三次出现）；settle 是放大项非起因；bottom 预算非限制源。附带发现：代码只有 post-step audit 无 pre-commit admission guard；ledger context 采样在 updateTilt 之前导致事件标签落后一子步。双角度滞回确认不能单独修复（不改 tilt 更新、不解决限流后空间均分）。

#### 倾角参考限速方案复核确认（v2.14 设计，动态可行域限幅）

designer 用反例证明固定 omega 不可行（720°/s 低 slack 不安全；360°/s 只把 12° 跳步降为 6°；跟手性下界 ±15° 需 ≥135°/s、±45° 需 ≥405°/s——单一固定值无法覆盖）。采用**动态可行域限幅**：每子步先收集材料 grant 计划 → 按安息角上限反推每边可行参考角区间 → 全边交集 → 期望角夹入；不可行则 hold 并报 BLOCKED（不先越界再修复）；两轮 pass 处理预算-角度循环依赖，O(cols)。数字核实（theta_safe=29.87°、5.85° 安全余量 vs 实际跳 12° = 2.05 倍超限）。

标定设计：7 个 omega 档对数扫描（90~720°/s），每档 ≥5 runs × ≥20 方向转换，P95 + bootstrap 95% CI；Pareto 决策（先剔硬安全失败档、再剔 P95>100ms 档、选最低安全代价；无候选同过 → 约束冲突交 manager，不降 tan30°、不加预算、不拍折中值）。

**预先暴露的战略风险**：±45° 跟手性下界 405°/s 与安全裕度要求可能冲突——若 Pareto 前沿无解，意味着 ±45° 大角度与跟手性在现有框架内不可兼得，届时需 manager 在「接受大角度响应变慢」与「重议大角度场景目标」间裁决。

#### GPU/性能问题的定位（对「响应变慢可用 GPU」的回应）

「响应变慢」拆为两个正交瓶颈：**①帧率掉**（实测 +15° 时 60→20/16 FPS，v2.8 无探针基线同样掉帧——渲染/物理负载问题，非观测探针引起）——GPU 化渲染管线、worker 化物理是正确方向，且 20 FPS 下 100ms 只有 2 帧，掉帧本身就是「不跟手」观感的一部分来源；**②角度限速**（可行域夹住参考线）——安全约束，GPU 加速不解除限速。另注意：物理计算本身仅 168 个数字/子步，计算量极小，帧率瓶颈更可能在 ArkTS 单线程/渲染重绘/IO，先 profile 再定位 GPU 用途。建议帧率归因加入七档 omega 标定的前置（掉帧噪声会污染 P95 统计）。

#### 更新后的行动序列

1. developer：ledger 对齐修复（updateTilt 后采样 context）——小改动先做
2. developer/effector：帧率掉帧 profile 归因（热点定位：渲染 vs 物理 vs IO）
3. designer/architect：pre-commit admission guard 设计（全通道 tan30° 提交前拦截，补上 post-step-only 的缺口）
4. developer：按 §17.10 实现 v2.10 观测协议扩展（加大角度相位，建议含 ±45° 过冲档与 ±15° 对照）——依赖 1 完成
5. designer：双角度滞回的逐边转折观测 + 95% bootstrap 标定（thetaStart/Stop 替换占位符，排除 30° 上端点）
6. developer：动态可行域限幅实现 → 7 档 omega 扫描 → Pareto 决策——依赖 2/3/4/5 全部完成
7. 汇合点：若 Pareto 无解（±45° 与跟手性不可兼得），manager 裁决大角度场景的目标取舍

## 一、澄清：现在的方案与这些文章是否同源

**是，同源，且要分两层说。**

### 1.1 本构层（何时流动、流动时应力多大）

P-011 的三个核心机制与本构文献同构：

| P-011 机制 | 文献对应 | 证据 |
|---|---|---|
| tan30° 硬门槛（§8 不变量） | Drucker-Prager 屈服 / μ(I) 准静态极限 μ_s（Jop 2005, GDR MiDi 2004） | sand6 `PhaseSolver.cc:214` 实现 μ(I)=μ+Δμ/(1+I₀/I)，场景 mu=0.4 |
| 26/20 双角状态机 | 屈服转变的非光滑处理（sticking/sliding 分支） | so-bogus `LocalSOCSolver.impl.hpp:300-380` 三态分支 + FB 半光滑牛顿；P-011 用迟滞替代 FB 是对边界抖动的工程化改进 |
| 静止零抖动 | 非光滑 vs 正则化的分野——正则化在静止端必然蠕行 | sand6 源码注释直接实证："PG without infinity norm leads to creeping" |

### 1.2 方程层（P-011 更直接的直系）

**P-011 的 128 列高度场 + 列间通量，本身就是深度平均（浅水型）离散**。这条线的谱系（浅水方程推导 PPT 第 33 页知识地图已给出）：

```
守恒律骨架（Dawson & Mirabito 2008，SWE 五步推导）
  → Savage & Hutter 1989（深度平均雪崩模型起点）
  → Pouliquen & Forterre（μ(Fr,h) 滞回摩擦）
  → Jop 2006（μ(I) 本构）
  → Gray & Edwards 2014（μ(I) 的深度平均黏性项 ν·h^(3/2)）
  → ReadPapers 245（完整深度平均 μ(I) 颗粒流模型——P-011 高度场的理论直系）
  → ReadPapers 250/251（偏析 segregation / 耦合 coupling——场景二双沙分选的理论直系）
  → Barker et al. 2021（μ(I)+分选耦合，OpenFOAM-muI 的科学基础）
```

**修正首轮评估的一处偏差**：首轮称「sand6/OpenFOAM-muI 不是浅水方程构建」，技术上指它们解完整方程（MPM/有限体积），这点成立；但由此推出的「浅水直觉只落在 P-011 自己身上」弱化了联系——Gray 学派线（245→Barker 2021）的模型**就是浅水型骨架 + 颗粒本构填充**，OpenFOAM-muI 的理论根基在这条线上。三仓库与 PPT 是同一理论的两个数值分支（深度平均 vs 完整方程），都对 P-011 有对标价值。

## 二、这些技术能不能用到现在的工程里

**分三档：可用的（现在就值钱）/ 对标用的（答辩与标定基准）/ 不能用的（结构不兼容）。**

### 2.1 可用（直接进文档与设计依据）

1. **26/20 推荐值的文献锚点**：tan26°≈0.488 落在粗颗粒/天然沙 μ_s 范围、tan20°≈0.364 接近玻璃珠 μ_s≈0.38（Jop 2005）——给 factory-recommended 一个跨材料区间的对标说明（对标 ≠ 标定，NOT_CALIBRATED 身份不变）。
2. **设计答辩材料**：「为什么用阈值状态机而非连续粘度」的依据 = 非光滑 vs 正则化的分野（so-bogus 结构 + sand6 蠕行注释）；「为什么 tan30 是硬门槛」= 安息角/屈服的本构来源。
3. **未来参数标定的对标基准**：观测③标定若重启，P&F 的 μ(Fr,h) 滞回曲线（PPT 知识地图明示的 slopeLimit 升级依据）与 Jop 的 μ(I) 参数面是现成的文献基准值参照系。

### 2.2 对标用（验收/效果判定时做参考答案，不进代码）

- **场景二分选**：Barker 2021 / ReadPapers 250 的分选理论可回答「重沙沉速 vs 轻沙沉速的比例设多少才像真的」这类标定问题——但 P-011 的沉降是现象学速率（vBottomCreep 等），不实现偏析方程，只做对标。
- **塌落时标**：sand6 `collapse.water.2d.conf` 的水耦合塌落场景可作 ±45° 崩塌时标的量级参照（不是验收线）。

### 2.3 不能用（结构不兼容，明确排除）

| 项 | 排除理由 |
|---|---|
| 代码级复用（MPM/锥求解器/FVM） | ArkTS 128 列高度场 vs C++ 全矩阵求解——计算预算（60fps 手机 CPU）与守恒/预算/guard 审计体系全部不兼容；引入即物理引擎重写 |
| 深度平均 μ(I) 黏性项（ν·h^(3/2)）直接移植 | P-011 用离散崩塌通道+预算替代连续黏性——这是「静止零抖动」的代价换来的结构差异（连续黏性在静止端正是蠕行来源）；245 的组件进 P-011 需重新设计离散对应物，不是移植 |
| P&F 滞回摩擦曲线直接拟合 | P-011 的 26/20 迟滞是现象学参数；引入 μ(Fr,h) 即引入速度依赖摩擦，与现有 relax 请求公式（残差驱动）是两套驱动语义，混用需 designer 层重设计 |

### 2.4 复用价值总评

**理论复用价值：高**（本构合法性、参数对标、设计答辩——全是现成的）。**代码复用价值：零**（三个仓库没有一个函数能进 ArkTS 工程）。**方法论复用价值：中**（sand6 的场景配置面/测试组织、so-bogus 的「局部解析解+全局迭代」分层思路，对未来测试场景设计有参考）。对当前 PIPELINE（观测③/P-012 渲染/correction）：无排期影响，不产生新任务。

## 五、交互借鉴：手指倒沙注入（2026-10-22，用户实测 knackpad 后提出）

> 用户实测 Falling Sand Game Online（knackpad.com/falling-sand-game）与 mysimulator.uk 沙丘模拟器后判定两者视觉效果均不达标（粗糙像素块/45° 硬锥/无速率限制的倾泻感——与 P-011 的验收口径差距全维度），但**「手指在屏幕上拖动持续倒沙」的注入交互值得借鉴**。本节评估其工程可行性。

### 5.1 借鉴点分析

knackpad 的注入交互值得要的部分：**手指按住/拖动 = 持续以指下位置为源添加材料**（可调笔刷/流速/材料种类）。它的价值在流沙画语境下是「补沙」——真实流沙画是封闭系统（沙量恒定），但产品化 App 的体验场景（清空重来、玩法扩展）需要受控补沙入口。

### 5.2 工程可行性：物理层已就绪，只缺 UI 手势层

代码事实核对（2026-10-22）：

1. **注入通道已存在且事务化**：`WaterSandField.inject(spec)`（:1191-1230）——完整校验（finite/非负/列范围/capacity 超限则 restoreBackup 回滚）、五相可选（water/heavy-deposited/heavy-suspended/light-deposited/light-suspended）、守恒基线自动重置（initialWater/totals）。**注入语义已过 P-011 的审计纪律**（注入是事件边界，`maxSandTopDelta` 无瞬移统计在 inject 边界重置——algorithm-P003-P005 §v2.2 既有约定）。
2. **手势层挂接点清晰**：SandCanvas 现有 PanGesture（:2528-2543）已被 P-011 手势倾角占用（tiltX 映射，canP011GestureOwnInput 门控）。注入手势需与之共存或互斥。

### 5.3 设计约束（若立项，designer 需先出方案）

| 约束 | 说明 |
|---|---|
| **手势互斥** | 拖动=倾角 vs 拖动=倒沙是同一手势的两种语义——需模式开关（长按切换已有先例 ：2520-2523，或面板按钮）或双指/单指区分；不得静默抢占倾角手势（P-011 观测 run 的手势所有权语义已被测试依赖） |
| **注入速率与预算的关系** | inject 是事件边界（不走 per-substep 预算）——但持续倒沙=高频注入，每次注入都 saveBackup/updateSandTop/audit，逐帧调用有成本；建议注入手势在 UI 层限频（如 10Hz 累积合并为一次 inject），且单次量走「笔刷列宽×薄层」的小量多注 |
| **相选择 UI** | 五相注入（水/重沙/轻沙×沉浮）——产品语义建议简化为「水/沙」两类+设定面板扩展，避免界面复杂化 |
| **守恒口径** | 注入改变总量（initialWater 重置已处理）——但观测 run / 回归测试期间注入手势应禁用（canonical evidence 模式强制），防止污染七相序列 |
| **体验定位** | 这是「玩法/工具」功能不是「物理保真」功能——真实流沙画不可补沙。建议进 EXPERIENCE 模式专属，TEST 模式禁用 |

### 5.4 结论

**可借鉴且成本低**：物理层零改动（inject 通道现成），工作量全在 UI 手势层（模式开关+指下位置到列区间的映射+限频）。但**它不改变流沙画核心体验**（封闭系统倾斜流动），属于工具性增项——优先级建议排在 P-012 渲染五维度与阶段一收口之后，不进当前 PIPELINE。若 manager 认可，立项走 designer（交互方案）→ architect（手势共存与观测隔离细化）→ developer 标准流程。
