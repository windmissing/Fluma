# G2.7 goals变更提案：按设备刷新率定义呈现流畅度 v1

日期：2026-10-22。责任：P-012 designer。依据本次用户转达manager **14:17“走goals变更流程”**裁决。状态：**PROPOSED / PENDING_GOALS_APPROVAL / NOT_VALIDATED**。本稿给目标、测量定义、成本与diff草案；不直接修改goals、测试评分/脚本或历史报告，不授权实现/真机采集。

## 1. 建议与修订理由

**推荐：`fpsFromPresentP95 ≥ 0.95 × R_test`，称“达到测试刷新率的95%”，不要简称“满帧”。** 保留`fpsP95`作为旧字段的版本化兼容别名；新methodId=`present-interval-p95-refresh-v1`。90Hz时门槛**85.5fps**，不向下取整为85；精确90fps是方向目标，不声称已达成。

| 项 | 旧规定/已知事实 | 本次处理 |
|---|---|---|
| [goals G2/G2.7](goals.md) | G2写“实测帧率≥100fps”；G2.7写`fpsP95≥100`，同时要求三相分类偏差≤5%、无瞬移 | 同步修订两处帧率措辞；分类偏差、无瞬移和全部安全目标不动 |
| [TC-WS-11](test-cases.md) | 前置≥120Hz，30s连续动态序列，≥100个WS_FRAME，`1000/p95(frameTimeMs)≥100`；低于100Hz按N/A | 新方案使90Hz设备可正式评价；旧规则下该设备是环境N/A，不追溯写旧FAIL或新PASS |
| [F1归因](fps-attribution-P012-v1.md) | 报告已测设备面板90Hz；旧34–60fps窗口和30s动态口径不同 | 在该测试显示模式下，真实唯一呈现帧率受90Hz制约，100目标不适配；每次测试仍需独立记录实际启用刷新模式 |
| [离屏模型验证](f1-offscreen-model-validation-v1.md) | 2–4ms blit来自CanvasPattern估算迁移；全幅blit、可缓存占比、RS成本未直接分离 | 撤销其作为决策级性能预测的资格；0.04ms或5–11ms也是外推，不作为新目标可达证据 |

选型理由：`fps≥R_test`不给测量抖动留下空间，且“达刷新率”没有明确时窗/分位数；`fps≥R_test（90Hz≥85）`数学上自相矛盾；固定85只适配一台设备。采用0.95比例是**提议的统一5%帧率容差**，不是从当前低性能结果拟合出来的及格线。它对应帧间隔容差`1/0.95−1≈5.263%`，不是“95%的帧按时”和“帧时容差5%”的混写；P95另定义尾部统计。该容差须manager按goals流程批准。

| 固定测试刷新率R_test | 新帧率线0.95R_test | 等价呈现间隔P95上限 | 单刷新周期（方向目标） |
|---:|---:|---:|---:|
| 60Hz | 57fps | 17.543860ms | 16.666667ms |
| 90Hz | 85.5fps | 11.695906ms | 11.111111ms |
| 120Hz | 114fps | 8.771930ms | 8.333333ms |

这不是所有设备上都放宽：120Hz档由100提高至114。各档由支持设备矩阵预先确定，不能看结果后选60Hz替代90Hz过线；非适用模式不与主档混合。第一梯队原≥30fps/≤33ms对应窗口和SV已通过门槛继续作为独立维持项，新目标不覆盖或降低它们。

## 2. 可测定义（随goals批准后冻结）

### 2.1 分位数对象与数据身份

令 `P_i` 为同一应用surface的**实际呈现事件**单调时间戳（ms，原始时钟保留ns或μs精度），事件携带frameId/surfaceId。只计唯一被呈现的应用帧，系统重复扫描旧buffer不能增加帧数；相同内容但确实新呈现的应用帧可计。`Δpresent_i=P_i−P_(i−1)>0`。

```text
sort Δpresent ascending → a[1..N]
p95PresentIntervalMs = a[ceil(0.95*N)]       // nearest-rank，1-based
fpsFromPresentP95 = 1000 / p95PresentIntervalMs
refreshAttainment = fpsFromPresentP95 / R_test
PASS候选主条件 = refreshAttainment ≥ 0.95
```

不对单帧瞬时fps先取P95：`P95(1000/Δ)`描述的是较快的一端，与`1000/P95(Δ)`不同。不舍入fps后判门槛；仅展示时保留小数。P95、P99、max间隔、总呈现帧数及平均fps均输出，后四项先作诊断；P95可能漏掉少数长卡顿，因此现有“动态无瞬移/无卡顿”主观及事件检查不能被它替代，不另行偷加或删除量表。

| 变量/来源 | 可用于什么 | 不可替代什么 |
|---|---|---|
| 实际present事件差Δpresent | 新G2.7主判，含渲染排队/合成/vsync/掉帧影响 | 不能仅用面板每次vsync扫描事件填满帧数 |
| 当前`WS_FRAME.frameTimeMs` | 当前代码在`SandCanvas.frame()`用两次`Date.now()`之差生成，表示应用回调间隔，含调度等待；保留为`callbackIntervalMs_legacy`诊断 | **不是纯计算耗时，也未经证明等于present间隔**；毫秒取整在90Hz附近足以影响门槛，不能直接改字段标签冒充新证据 |
| `physicsTimeMs`、未来CPU/render/RS区间 | 定位临界路径与热段；单独记录并注明时钟 | `1000/P95(workDurationMs)`只表示工作吞吐代理，不能当呈现FPS；各阶段P95不能相加/相减成总P95 |
| HUD、录像编码fps、postFrameCallback时间 | 辅助核对/用户体验证据 | 不替代实际present。现FrameCallback已传ns时间仍只是回调时间，不能假设它就是上屏时刻 |

与[架构§7](architecture-P012.md)既有presented-frame数据纪律对齐：tester先探测设备工具能力，冻结实际可用的trace事件/时钟/字段；本稿不编造SDK事件名。拿不到可信present时间戳或无法关联应用surface，输出`PERF_BLOCKED(DATA_SOURCE_UNAVAILABLE)`，可继续性能诊断，不以回调FPS签G2.7。

### 2.2 刷新率基准：不能用低FPS反算低门槛

`R_test`是采前登记的设备/分辨率/电源策略下**应用目标surface获准的固定显示刷新模式**。本批目标90Hz须记录设备ID、系统版本、显示modeId、分辨率、采前与窗口内模式日志/trace；不是营销面板峰值、HUD FPS或`1000/回调中位数`。面板支持90但应用被系统固定60时，标`REFRESH_MODE_NOT_ESTABLISHED`并定位配置/调度，不把R_test降到60声称90档达成。

如果允许可变刷新率，另开方法revision按预注册刷新区间评价；本版不取全窗平均刷新率。窗口中发生系统模式切换/后台/外部遮挡，保留完整记录并标环境条件不满足；不得裁掉慢段重算同次PASS，也不得因热降频而自动降低R_test。热态场景属于后续支持范围时须作为独立配置验证，不能择优弃run。

### 2.3 TC-WS-11的30s窗口对齐

沿原操作顺序，明确时轴和剩余4s，禁止另找最好滑窗：

| 时间 | 原用例动作 |
|---|---|
| [0,5)s | +15° |
| [5,10)s | −30° |
| [10,13)s | shake=1.0 |
| [13,18)s | 静置/沉降 |
| [18,22)s | 倒立（沿已审计事件式invert180语义） |
| [22,26)s | 回正 |
| [26,30)s | 原规定的回正动态倾斜；具体轨迹由tester在schedule/seed/hash中采前固定，不按结果调整 |

窗口从脚本启动事件T0取 `[T0,T0+30s]`，设备时钟与输入/物理时间对齐。必须完整保留静置5s、重载shake/翻转、dormant和真实长间隔，不筛选`substeps>0`重算主判；另按上述阶段输出诊断。静置时若应用复用旧帧并不提交，不以重复扫描伪造新帧；这会产生较长present间隔，须原样计入并说明，不暗中把省电策略换成测量豁免。

采集窗口前后各保留足以包围边界的present事件；统计与窗口相交的完整帧间隔，不把跨边界的长间隔截成短值。预热在T0前完成且不得按结果延后T0。首尾没有包围事件时为`BLOCKED(incomplete_window)`。同一时钟内要求frameId/trace序列与采集完整性闭合；丢帧是实际长间隔，**日志丢失/事件漏采**是测量不完整，两者分开。

保留原≥100有效样本下限，同时要求完整30s与无未解释采集缺口；100条稀疏WS_FRAME本身不足以验收。90Hz名义30s约2700次刷新，仅作计数合理性检查，不要求伪造2700个新呈现帧。采集失败/缺钩子报BLOCKED；完整且达到最低样本数的测量低于线报FAIL。若完整采集却因真实极慢呈现不足100，报`BLOCKED(insufficient_present_samples)`并同时披露真实帧数/长间隔，不标环境N/A或PASS，不通过裁掉慢帧、延长窗口凑样本。现有多次/分段取最差的评分纪律保留；重复数沿正式测试计划，不擅自减少，不合并所有run掩盖最差run。

## 3. 可达路径与证据等级

需要同时审计**渲染/合成/调度**和**物理重载**；离屏预合成是前一路候选，不是已证明必需或充分的唯一方案。即便GPU/CPU重叠，也应看真实临界路径与数据依赖，不能将不同帧的物理结果错配以填满画面。

| 输入结论 | 本提案采信程度与修正 |
|---|---|
| F1重载物理约90ms、中轻载约13ms | 足以要求物理侧单独治理；旧frameTime是回调间隔，仍不能当正式present测量。单独把物理90降到35ms仍大于90Hz周期11.11ms，**不能叫90Hz路径已闭合** |
| “render+other≈15ms” | 可作回调区间扣除已记录物理时间后的残量；包含等待/同步/其它，不能全归为E/A可省光栅成本。`P50(frame)−P50(physics)`也不能替代逐帧相减后统计 |
| C消融P95增量−1.01ms/接近0 | 说明该配对下未分辨出增加成本；**不能推出每次drawImage≤0.012ms的严格上界**，更不能按面积直接证明全幅blit=0.04ms |
| 新模型5–11ms、blit0.04–2ms | 均为低置信候选区间，不作为预算兑现；第一批实测要辨认到底省了哪一段，RS仍未知 |
| 静止17ms或90Hz面板 | 17ms回调节拍不证明GPU忙了17ms；90Hz下两刷新周期是22.22ms，不是16.67ms。报告“60Hz两拍”解释需调度trace核验，不带入新目标论证 |

预算必要条件示例：90Hz新线对应11.695906ms，精确单周期11.111111ms。若同帧关键路径是串行 `Tphysics+TrenderSubmit+Tsync`，必须把该路径压进相应期限；假设非物理实际占3ms（**情景假设非实测**），精确90Hz只剩8.111111ms给物理。90ms重载即使忽略渲染也需约8.1倍缩短才到11.11ms；这只是必要量级，不是优化可获得倍数或逐阶段P95求和证明。

物理候选方向为剖析guard/preview重复工作、账本与数组分配、重载子步/扫描热点，先做等价缓存/复用的可证明优化；涉及并行、步长或求解机制改变需重新架构/算法审查。不得减少物理列、少算时间、跳过guard/守恒/预算或改输入角度来换FPS；准确性和实际输入响应不能延期。

## 4. 第一批测量与成本排期建议（未授权执行）

以下为人日估计，不是真机占用时长承诺；现有工具若缺present/RS数据需单列风险。先批准诊断任务，不能将“0.5天”写成离屏架构交付估期。

| 顺序/路线 | 工作、交付与退出条件 | 估计人日 |
|---|---|---:|

| P2 全幅blit原型/测量 | 既有尺寸位图构造期烘焙＋帧内drawImage；同内容空操作/直接绘制/缓存blit三臂，测初始化峰值、热态提交、上传和端到端；与E3平台绕道工作复用 | 1.0，平台路径不通则另估 |

首轮建议只排P0–P3：约**2.5–3.0人日**，其中P1的0.5天先回答静态缓存是否值得做；不是承诺1.5天能消除所有低置信分量。P1/P2不能自动测到RS下限，也不能解决重载物理。后续成本依据实际结果再由manager决定。

消融纪律：省略静态层是诊断，不可当完整画面优化版验收；全关静态层的收益也不是缓存收益的严格上界，因为提交、合成、像素覆盖与vsync可能非线性。必须记录候选静态层何时失效：雾tau随悬沙/层高/相位变化，不能将“预烘焙噪声”误作“整个雾层永远静态”。P1取得的是在指定输入下的敏感性，不凭draw数量估计可省毫秒。

模型报告已记录帧循环OffscreenCanvas putImageData平台问题；建议复用E3已验证绕道或构造期原型，**不把未知的动态上传路径计为已解决**。若连续动态无法合法更新缓存，应报告该候选不可用，不能靠不更新画面/关闭效果达帧率。
