**逐项核对结论**：4+37=41 新增、41−32=9？**不对——净 18 = 4 + 37 − 32 = 9？** 数学校验：4+37−32=9 ≠ 18。**T320 的净 18 分解存在算术缺口**（卡面「核净18逐条计数是否完整闭合（报告列4+37−32不等18，不能漏项）」正是要求查这个）。缺口 = 18−9 = **9 条未归因记录**。本卡补查：

T320 报告 §三表格是「新增 28 条、旧消失 10 条，净增 18」（T316 原文），而 §三分解表给 4+37−32。**两组数字来自不同口径**：28/10 是 T316 的 file/owner/text/reason 对账（净 18 的来源），4+37−32 是 T320 尝试按 reason 细分。若按 T320 的 reason 细分口径，4+37−32=9 与净 18 不符，说明 reason 细分漏了 9 条（可能是 28 新增里非 Date.now/非 CONTEXT_LIMIT 的其余类别，或 32 消失未全列）。**收口义务转移**：T320 的 (owner,text) 集合等价证明（39 显式位点）不受影响，但净 18 的 reason 级分解表**不完整**——列入 §3 工具收口清单第 2 项（tester 补 28/10 条的逐条 reason 清单），**不阻塞主裁定**（净 18 本身由 28−10 的 file/owner/text 对账支撑，T316 已给）。

## 2. Date.now 证明边界（PROOF_GAP 的准确定性）

T320 判定正确且本卡确认维持：
- **规范层无分配要求**（ECMA-262 §20.4.2.1 返回 number）≠ **实现层无分配**——方舟运行时 Date.now 的 native 实现不可从项目源码证明；
- 运行佐证（T312 真机 32 行稳定、97 项自测）**不能替代静态证明**——「PROOF_GAP」定性正确；
- 旧 `TxWorkTrace.clock` 同类问题先在（开工前图已有）——不能只豁免新两处。

**本卡裁定：PROOF_GAP 是「运行时原语证明义务」，其收口路径只有两条，且都不在本项目工程侧**：
1. **目标运行时原语摘要工具**：需要方舟/HAP 运行时的 native 分配摘要（类似 valgrind/mimalloc 的原语级标注）——项目外部工具链能力，**tester/静态工具维护者无法从项目源产出**；只能待运行时团队或逆向工具提供，不可预期排期；
2. **热计量移位（工程侧唯一可执行路径）**：把 Date.now 从热路径移除，改用注入的单调时钟原语（若注入原语同样有分配嫌疑，则移到「调用计数」——纯整数递增，诊断导出时再换算）。

**裁定：采路径 2（热计量移位），且是有限改动的工程方案**：

### 热计量移位合同（developer 实施卡输入）

- `P011HotWorkReceipt.begin/end` 的 `Date.now()` → 换成 `performance.now()`？**不行**——同样有实现层不可证问题。正确方案：**注入时钟回调**（页面侧已注入 `systemDateTime.getUptime(ACTIVE,false)` 单调毫秒先例，T154 报告 §页面只注入单调时钟）——但注入回调本身是函数调用，分配义务同样未证。
- **最终方案（零原语依赖）**：热路径只记**调用序号**——`beginSeq/endSeq`（uint64 递增，`++` 无分配可证性争议），时间戳**完全移出热路径**；诊断导出（冷）时用「序号 × 已知采样率」或接受「无时间戳只有计数」的降级语义。代价：阶段耗时从 wall ms 变 call count——**语义损失**（T311 的 inclusive ms 计量消失）。
- **权衡明示**：该方案牺牲 T311 计量的时间维度。若 manager 判定时间维度必须保留（watchdog 归因依赖 ms 数据，如 T312 的 5.45ms/R），则热 Date.now 保留、静态门 PROOF_GAP **永久开放**——**二选一交 manager 裁决**（卡面「用例超工具原能力 manager 裁决」正是此情形）。本卡建议：**保留 Date.now，PROOF_GAP 如实登记为已知不可闭合项**，理由：T312 真机已证 watchdog 归因离不开 ms 计量，静态门的零分配断言在该原语上让位于运行时诊断价值——这不是「无据白名单」，是把 PROOF_GAP 从「待闭合」改判「接受的成本」。

## 4. 结论与路由

- **静态 FAIL 维持**：NOT_ZERO_ALLOCATION/164 不变，零分配形式门不闭合不放宽（T316/T320 判定维持）；
- **不阻 GPU**（T316 原判维持）：零分配门是 CPU V2 侧的形式门，GPU 主线（T324/T317/T318）不受影响；
- **T312 长期稳定说法勘误**（卡面点名）：T320 §四引用「T312 真机 32 行计量输出、长期运行稳定」作运行佐证——本卡核实 T312 原文：**低剂量 run 63414 进程 >20 分钟存活**（单事件 ≤1.4s 未达 watchdog），另两 run 死于 THREAD_BLOCK_6S——「长期稳定」只能指低剂量 run，不能泛化到满注入 run。T320 的引用**范围收窄但非虚假**：97 项自测+低剂量长存活仍是运行等价的佐证，但**满注入下 watchdog 已证会杀**（T312 §二），Date.now 不掩盖此事实。勘误登记，不改 T320 结论。
- 路由：§2 热计量移位（若 manager 采纳）→ developer 小卡；§3 三项 → tester 工具卡（可与 T162 子探针实施合并）；manager 裁决项 = §2 的二选一。
